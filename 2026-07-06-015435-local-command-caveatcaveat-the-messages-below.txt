● Yes — on Android it's genuinely possible, and it's exactly how real anti-scam
  apps (Whoscall, Google's own scam protection) work. On iOS it's flat-out
  impossible, so this is an Android play. Here's the honest picture:

  How it works on Android — AccessibilityService

  An Android app can register an accessibility service (the user grants it once
  in Settings). That service can:

  1. Know you're in TNG — it receives window-change events with the foreground
  package name (com.tngdigital.ewallet), so it activates only there.
  2. Read the transfer screen — instead of the DOM, it reads the accessibility
  node tree: the recipient name, amount, and notes on TNG's DuitNow confirmation
  screen. Your site_adapters.js concept ports directly; it becomes a "screen
  adapter" that pattern-matches node text instead of CSS selectors.
  3. Interpose the warning — it draws a system overlay on top of TNG (the same
  spinner → verdict → "Cancel / Send anyway" card as your extension), calling
  your existing /api/screen unchanged. Warn-only, never blocks money — your
  product thesis survives intact.

  So the whole backend, agents, and verdict pipeline stay exactly as they are.
  Only the "content script" layer is rewritten in Kotlin.

  The three caveats you must know before committing

  - TNG fights this. TNG eWallet ships malware protection that detects
  sideloaded apps holding accessibility permission and can refuse to run —
  ironically, the same mechanism scam malware uses is the one we'd use to stop
  scams. For a hackathon demo this is manageable (emulator, or present it as
  "this is why banks/wallets should integrate Sentinel officially"), but it's
  the real-world blocker to be upfront about with judges.
  - TNG is a Flutter app, so the accessibility tree is flatter and less labeled
  than a native app's. Reading the confirmation screen is doable (Flutter
  exposes its semantics tree when an accessibility service is active) but the
  adapter needs tuning against the actual app.
  - Play Store policy restricts accessibility APIs, though anti-fraud is an
  accepted justification category. Sideloading for the hackathon sidesteps this
  entirely.

  What building it takes

  A native Kotlin app (React Native/Expo can't do this without native code
  anyway): accessibility service + foreground-app detection + TNG screen adapter
  + overlay UI + your existing API. That's roughly 2–4 focused days for a
  demoable version — the risky part is the TNG screen adapter, which needs a
  real device with TNG installed to inspect its node tree (there are inspector
  tools that dump it, analogous to your DOM-dump pipeline).
